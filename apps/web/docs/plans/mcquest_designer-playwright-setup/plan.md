### Risks
**Primary Risk: React Flow Testing Complexity**

**Challenge:**
Testing drag-drop and graph interactions in React Flow can be unreliable.
- Mouse events need precise coordinates
- Graph state changes may be async
- Node positioning can be non-deterministic
- Edge creation requires accurate dragging

**Mitigation Strategies:**
1. **Reference Existing Tests:**
   - Review apps/web/e2e/quest-editor.spec.ts before deletion
   - Extract working drag-drop patterns
   - Document what worked/didn't work

2. **Incremental Testing:**
   - Start with simple interactions (node selection, click)
   - Build up to complex actions (drag, edge creation)
   - Test each interaction type in isolation

3. **Reliable Selectors:**
   - Add data-testid to React Flow nodes/edges
   - Use stable identifiers for graph elements
   - Avoid position-based selectors

4. **Explicit Waits:**
   - Wait for graph to stabilize after mutations
   - Check for animation completion
   - Verify state changes before proceeding

5. **Fallback Approach:**
   - If drag-drop too flaky, test via state manipulation
   - Call editor store methods directly
   - Verify UI reflects state changes

**Secondary Risks:**

1. **Clerk API Learning Curve**
   - Need to research Clerk Backend API for user management
   - May require trial/error for test user workflow
   - Mitigation: Start with manual test user, automate later

2. **Test Database Configuration**
   - DATABASE_URL_TEST env variable management
   - Prisma migration strategy for test DB
   - Mitigation: Copy dev DB setup, just different URL

3. **Test Speed**
   - E2E tests inherently slower than unit tests
   - Video/screenshot capture adds overhead
   - Mitigation: Parallel execution, optimize selectors, skip slow tests locally

4. **Visual Baseline Management**
   - Screenshot diffs can be sensitive to small changes
   - Cross-platform rendering differences
   - Mitigation: Generous thresholds, update baselines intentionally

**Risk Level: MODERATE**
Manageable with incremental approach and learning from existing tests.

**Page Object Model: Comprehensive**

- **Full encapsulation:** All page interactions through page objects
- **No direct selectors in tests:** Tests read like user stories
- **Strict abstractions:** Each page/component has dedicated class
- **AI-friendly:** Clear, discoverable interface for each page
- **Reusable components:** Shared UI elements (navbar, panels) as separate objects

**Example Pattern:**
```typescript
// Test file (high-level, readable)
test('create new quest', async ({ page }) => {
  const dashboard = new DashboardPage(page)
  const editor = await dashboard.createNewProject('My Quests')
  
  await editor.createQuest('First Quest')
  await editor.inspector.setTitle('Updated Title')
  await editor.inspector.setDescription('Quest description')
  
  await expect(editor.canvas.questNode('First Quest')).toBeVisible()
})

// Page object (detailed implementation)
class EditorPage {
  constructor(public page: Page) {}
  
  get canvas() { return new EditorCanvas(this.page) }
  get inspector() { return new QuestInspector(this.page) }
  get chapterPanel() { return new ChapterPanel(this.page) }
  
  async createQuest(title: string) {
    await this.page.getByTestId('create-quest-btn').click()
    await this.inspector.setTitle(title)
    await this.inspector.save()
  }
}
```

### Patterns

### Data & State
**Test Database Strategy:**
- **Isolation:** Separate PostgreSQL database (DATABASE_URL_TEST)
- **Reset:** Truncate all tables between test runs (faster than drop/recreate)
- **Schema:** Same Prisma schema as dev/prod
- **Migrations:** Applied before first test run

**Clerk Test User Management:**
- **Mix Approach:**
  - Persistent users for basic auth tests (created once, reused)
  - Per-test users for specific scenarios (created/deleted in test)
- **API-based:** Use Clerk API for programmatic user creation/cleanup
- **Credentials:** Store in .env.test or test fixtures
- **Cleanup:** global teardown removes per-test users

**Test Data Creation:**
- Use Prisma client to seed test data
- Leverage existing schema factories (createDefaultSnapshot, createDefaultQuest)
- Create page object fixtures that encapsulate data setup
- Store common test data in fixtures/

**State Management:**
- No shared state between tests
- Each test starts with clean database (truncated)
- Clerk users managed per strategy above
- Autosave disabled or mocked to avoid timing issues

### Error Handling
**Test Error Handling:**

1. **Assertion Failures:**
   - Clear, descriptive error messages
   - Include context (page state, expected vs actual)
   - Automatic screenshot on failure
   - Trace file for debugging

2. **Setup/Teardown Failures:**
   - Fail fast if database unreachable
   - Fail fast if Clerk unavailable
   - Clear error messages about environment issues
   - Suggest fixes (check .env.test, run migrations, etc.)

3. **Flaky Test Handling:**
   - Log failures for investigation
   - No automatic retries initially (fail fast to identify issues)
   - Document known flaky tests
   - Fix root cause rather than mask with retries

4. **Debugging Artifacts:**
   - Screenshots saved to test-results/
   - Videos saved to test-results/
   - Console logs included in test output
   - Trace files for detailed debugging (trace.playwright.dev)

5. **Error Categories:**
   - **Environment errors:** Missing env vars, services unavailable
   - **Test errors:** Assertions failed, selectors not found
   - **Application errors:** Console errors, network failures
   - Each category has specific debugging guidance in docs
